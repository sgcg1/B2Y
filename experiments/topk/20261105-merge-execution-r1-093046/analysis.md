# 实际归并r1：编译完成，但同步守卫拒绝执行

2026-11-05，来源提交9c89df7。用户同时上传JSON/log及1片+manifest；无损还原的分片报告与直接上传JSON逐字节相同。原始文件大小与SHA见metadata.json，生成代码及stderr来自JSON内嵌证据，全部SHA已核验。

## 实际完成到哪一步

R128/B32与R256/B32均完成TileLang编译，生成了CPP；随后编译stderr包含ThreadSync警告，运行器按守卫拒绝执行。两档未进行设备结果检查，也未编译B1计时版本，因此设备归并正确性未知、计时样本为0。CPU64项实际AST检查通过只说明顺序逻辑，不覆盖SIMT同步。

## 警告是什么

编译器明确警告：把同步从不安全的分歧if内部外提，无法分隔仍在分支内部的冲突，race remains。两处条件分别出现在头块有效性判断与`j<own && take>0`排名主体。生成CPP包含外提的asc_syncthreads。

本轮不能通过禁用守卫或仅凭CPU结果继续执行，也不能认定已观察到实际设备错误：归并内核根本没有运行。现有写法存在编译器未能安全处理的内存访问/控制表达，必须改变结构并检查生成代码。它不推翻上轮已通过的独立消费数方法。

## 独立r2重试

[新的r2入口](../../../diagnostics/topk-merge-execution-r2/README.md)保留同一精确排名归并算法与32组输入，R128/R256不变。将动态side/源/共享读地址明确限制到所属数组；头块填充使用条件值加无条件共享写；排名计算只写线程局部值，将左排名共享写移出lane有效性分支。没有无依据的T.assume、未关闭ThreadSync检查。

改写后CPU实际AST64项检查通过，仍核验全部键/索引、每批消费、越界和每个有效输出恰有一次归并写。尚无r2设备结果；同步守卫必须仍通过才能进入执行，若仍诊断则继续停下分析。

此修复针对设备代码表达的安全性，不是新增性能优化结论。无全算子性能数据，不计算相对TopKV2倍率，不把失败当作rank-merge已跑慢。
