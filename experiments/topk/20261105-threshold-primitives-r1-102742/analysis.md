## 性能应如何解释

encode_keys独立kernel从GM读分数，按当前SIMT表达生成完整键，并将16384个键写回GM；46.002μs包含该额外写回。

collect_given_threshold在同一个kernel内读分数、构建UB完整键、分组计数、128组串行小前缀、稳定收集及初始化输出，阈值由CPU提供；67.951μs不包含四轮精确阈值选择。它没有调用原生SIMD压缩。

**两个时间不能相加，也不能用两者相减得到“纯收集成本”。** 两者数据驻留、GM写回、融合布局不同。不能据此推导完整T耗时、正式ops-math倍率或DT32核性能，也不能把这两个数作为所有可能实现的成本下界。

可以明确判定：当前这两种SIMT表达与此前假设的低固定开销预算不相容，不应直接拼入低延迟完整T。即使先免费提供正确阈值，这条具体收集表达仍需约68μs。该结果不证明原生SIMD键变换或收集同样慢；后者尚未测试。

Profiler日志里的“won't be using warmup”针对每个独立窗口的schedule；kernel已在窗口外预热3次，不应误判为没有预热。5样本/方法、单进程，只用于部件成本初判，不包装成完整算子三轮稳定测量。

## 本轮最重要的新发现

顶层导出检查没有hist/sort/merge/compress/gather相关命中，但源文件清单发现了：

- 现场`tilelang/ascend/language/simd.py`，SHA256 `9a7403dadb15ab5842988deb33d90bfbaec2f916ebc6de3bae273de1a611c302`。732/734行是bin=0/1校验，756行说明uint8向量→uint16频数直方图，765行说明累计直方图。
- `src/ascend/codegen/codegen_ascend.cc`，SHA `e406224ad3c3a33050e1125ee3495ba35f531e4148ad0f4a80a03a5bedc30d6e`，2099行存在SimdVF histogram处理注释与参数说明。
- `src/ascend/codegen/codegen_pto.cc`记录histogram可变向量目标及4参数约束；builtin.h也有histogram相关声明线索。

完整清单见backend-inventory.json。扫描366份源码、约7.0MB；未触发清单数量截断，但仍只覆盖声明的限定目录，不能冒称全工具链穷尽检查。

这足以纠正“顶层枚举没有hist，就无法表达”的推论。**能力很可能位于嵌套SIMD命名空间，而非顶层T.histogram。** 不过目前回传的是匹配行，不是完整函数签名与可运行示例；没有实际调用，也没有生成相应直方图指令，更没有性能成绩。不能把源码中有实现线索直接写成“硬件直方图已验证”。

本地另一个TileLang版本可看到同类函数，但其simd.py哈希与现场不同，不能照搬本地签名冒充现场版本。下一项必须直接核对现场模块的定义、向量类型、可变目标分配、mask与bin语义。此前部分SIMD尝试使用不存在的alloc_frag等接口，不能重复猜接口的做法。

## 决策与下一道关卡

本轮无需重跑；不继续调当前SIMT采集表达，也不把它直接接入完整T。原路线仍是待验证候选，不因这两个SIMT成绩就宣布整个阈值算法失败。

下一步应明确针对真正SIMD路径：

1. 读取现场嵌套simd模块的精确签名/源码，以及匹配codegen处理；保存SHA。不以不同仓或不同版本源码替代。
2. 若接口契约确认，最小测试频数直方图与累计直方图：覆盖两个128桶分区、跨向量累积、mask、全同值、极端桶及分布，并核验生成代码与原子/串行模拟的区别。累计语义必须与CPU oracle明确对齐，不能仅看函数名。
3. 独立测试真实SIMD完整键变换；读取实际mask/比较/位运算表达，不再用T.Parallel/SIMT结果当SIMD成本。
4. 最后确定合法的原生压缩/收集方法与预算，再决定完整T是否值得实现。未确认关键操作前，不使用条件预算8–14μs等推演当预期结果。

当前有价值的进展是：精确数据流正确性得到验证，慢表达被测出，且找到此前顶层API枚举漏掉的具体SIMD源码位置。尚没有新的完整算子性能结果。
