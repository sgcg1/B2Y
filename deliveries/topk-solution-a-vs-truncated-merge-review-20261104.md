# 方案A与分块截断归并：独立审查与比较

2026-11-04。审查用户指定的`topk-solution-a-design-20261104.md`，同时阅读其vhist能力探针。未执行探针、未改动对方设计或代码；以下是审查意见，不把文档中的执行要求视为用户已要求运行。被审文件版本、SHA、行号及算术见[证据](../analyses/topk/20261104-solution-a-vs-truncated-merge-review/review-evidence.json)。

## 判断

**A的向量计数、数据驻留和统一收集方向合理，潜在工作量可能低于比较排序；但当前文档尚未给出可实现的完整算法，8–14μs预算及“0.8可达”结论不成立为证据。** 最严重缺口是跨核数据流、分数驻留与最坏边界精化，而非缺少某个小优化。

我的截断归并方案在算法闭合、精确剪枝证明与CPU正确性原型方面更完整，适合进入硬件表达验证；但没有NPU数据证明它更快，也有排序成本、归并集中和记录打包风险。不能仅凭方案完整度选出性能赢家。

## 1. A的跨核数据流尚未闭合（阻断实现）

A的S1设定P≥4，各核的hist_w与coarse缓存位于本核UB，却直接写“归并P个hist→全局hist，寄存器/UB归并，非GM”。这省略了数据如何离开所属核、谁读取它、核间如何同步以及阈值/偏移如何返回。

官方[内存层级](https://asc.gitcode.com/guide/programming_guide/advanced_programming/advanced_ai_core_programming_model/simd_simt_hybrid_programming/memory_hierarchy.html)明确UB为单核内共享内存；同核VF之间可复用，不等于所有核共享同一个UB。官方[CrossCoreSetFlag](https://asc.gitcode.com/api/SIMD-API/basic_api/sync_control/inter_core_sync/CrossCoreSetFlag_ISASI.html)提供核间完成通知/等待；同步接口本身不等于自动聚合或搬运其他核UB中的数据。

可实现的补法是明确GM小缓冲与同步/广播，或者证明当前硬件与TileLang支持某条特定跨核通信路径；也可以改为单核常驻算法。三者成本与并行结构不同。若拆成多个kernel，不能默认前一个kernel的UB局部缓存可供后一个kernel继续使用。并不否定单kernel内同核VF保留UB的可行性。

S3的“本核分段槽位”也需要具体偏移：令a_w为本核高于阈值数量、b_w为等于阈值数量，out偏移需prefix_sum(a_w)，边界缓冲偏移需prefix_sum(b_w)。仅有全局t/before/b这三个量不足以分配不重叠的精确槽位。全局partial hist若确实汇聚到leader，可由其计算这些偏移；但这条通信与返回路径必须写入算法及预算，不能同时删除offsets却不提供替代。

## 2. 只缓存粗键，无法同时做到只读一次x并收集精确分数

S1只明确缓存uint8 coarse；S3又要求不再读GM x，却要收集(index,score)。coarse是多对一映射，无法还原完整FP32分数，也无法凭它精确确定边界中的前q项。

至少选择其一：①保留本核原始分数或完整32位键至S3/S4；②再读取x；③把必要键/分数写入中间缓冲。若选择①，应增加64KiB整行分数或完整键的分布式驻留预算，说明跨阶段生命周期和精化位置。当前只写coarse_cache且声称1趟x读，信息流不完整。

## 3. S4仍是最关键的算法占位符（阻断整体评估）

“对b条候选精确选q个”重新提出了TopK子问题，尚未说明使用排序、radix选择、阈值归约还是其他算法，也未给出精确同分规则实现。不能据“并行、小候选”推导为O(1)精化或固定2–4μs。

b≈894只是当前随机样本。同分/量化/接近FP32时b可达16384，每核收候选、精确选择、tie和最终收集如何执行必须明确；若仍只留2048容量，就会重现本轮审计要消除的断崖。若留全量，则应计入空间与通信。

A可选择我的截断归并作为S4，但那会成为明确的混合算法，需要重新计算其局部候选、搬运、kernel和最坏成本，不能继续沿用当前2–4μs估计。

## 4. 成本表混用了当前未发生的工作（重要事实错误）

A第3节把当前894边界路径的score_key计算写成“≈7152+tie32768”，并把两次全窗tie扫描算入该随机样本。固定5eb130ef保留组合已缓存完整键，普通路径初始化时对894个边界分数各算一次score_key，后续扫描读keys。ADAPTIVE_TIE下全窗tie尾段只在meta[2]>2048时进入，本轮894不进入。

因此该样本score_key不是894×8再加32768，所谓约90%减少不能作为当前对照。原子数≈39888、8轮×2串行前缀、约64个VF主体同样缺少同轮实际计数依据；EARLY_EXIT会跳过quota归零后的主体。固定循环控制仍有同步，不等于每轮都执行8个完整VF。

A对旧低效结构的方向判断可成立，但收益必须对照现在实际测量的保留版本，不能混合普通与溢出、缓存前后的成本来放大。

## 5. 当前能力探针不能决定“高效向量直方图可行”

已读`kernels.py::hist_bucket_reduce`：它为每个桶启动逻辑工作者，再在T.serial(N)中逐项比较digits[j]并累计。代码自身也标注O(256*N)。N16384时是4194304次逻辑桶比较，并非16384项一遍生成256桶的原生向量histogram。

这一写法本来就没有atomic。生成CPP不含atomic，只能证明未出现该类操作，不能证明编译器把419万次比较变成高效hist指令；也不能证明内层串行累加被SIMD化。需要确认生成的指令/调用结构、工作量及设备耗时。0原子可能比原子路径更慢。

探针可以用于API枚举、编译形态观察和两种表达的一致性检查；当前没有设备计时，不能为S1的3–5μs背书。共享_coarse_byte意味着两种输出一致仍非独立数值oracle；边界/特殊值应另核验。报告采集completed也不等于算法通过，因为cross_check是记录布尔值而非验收判定。

(b)“多bank私有直方图令原子降P倍”也需更正：若仍每个元素执行一次更新，总逻辑更新仍为N；分bank降低的是每个地址/核的争用，之后还增加归并，除非另有聚合机制才会减少更新次数。不能把并行度直接当成操作数收益。

运行层面探针未自动检查npu-smi占用、Python默认为python3而非固定已用路径，回传仍让用户复制文本而非既有B2Y结果流程。它不修改主算子是优点，但当前不宜直接当成熟的一键性能关卡。此处不修改它，也不要求用户现在运行。

## 6. 时间预算目前是目标，不是保守估计

分段最小值严格相加为7.5μs，最大14μs；文档取整写8–14μs。以现有10.639μs参照，8–14μs对应约0.760–1.330x，14μs不满足0.8x，更未稳定优于1.0x。

3–5μs histogram、0.5–1μs scan、2–4μs collect/refine都无原语实测；跨核归并、广播、偏移、全量边界路径、scratch及同步尚未计入。因此“保守”及“0.8可达区”应改为未经验证的预算目标。

0.8在历史issue与目标分支文档中存在门槛表述差异，交付契约已经记录；用户目标是同环境稳定优于TopKV2，不能以达到0.8作为任务完成。

## 7. 两个方案的公平比较

| 维度 | A：粗分桶+向量阈值/精化 | B：分块精确排序+截断归并 |
|---|---|---|
| 核心算法 | 仍是粗筛后边界子问题；S4未定义 | 局部TopK与每层MergeTopK均已定义 |
| 正确性闭合 | 若通信、分段偏移和精化正确则可成立；当前缺具体实现/完整证明 | 剪枝证明完整，独立CPU原型30例通过；不是NPU验证 |
| 平均工作潜力 | 边界小时可避免排序大多数数据，可能更少 | 所有输入承担局部排序与归并，算术工作可能更大 |
| 最坏分布 | b可达N，成本未交代 | 同一截断归并树，无桶容量fallback；实际耗时仍可能随数据变化 |
| 核间通信 | 多次依赖全局统计/阈值/偏移，路径未定义 | 两kernel间显式GM候选与顺序依赖，内部归并单block |
| 数据驻留 | 仅coarse不够；需补完整键/分数或再读x | 已明确64KiB候选、200KiB逻辑全路径GM流量 |
| 核心原语风险 | 高效histogram、scan/压缩、跨核协调、S4精化 | 完整键+索引排序、批量归并与消费数统计 |
| 并行性风险 | P块不保证4倍加速，精化分工尚未定义 | 最终归并集中单block，可能成为瓶颈 |
| 内存风险 | 分布式驻留和b=N候选空间未核算 | 逻辑记录尺寸不等于物理sort布局，scratch尚需验证 |
| 性能证据 | 无新TopK设备结果；预算未验证 | 无新TopK设备结果；同样不能承诺优于10.639μs |

A与当前实现同属粗筛/精化家族，主要创新集中在硬件表达、驻留和并行组织；B改变了核心选择机制为比较/归并。家族相同不等于一定无效，家族不同也不等于一定更快。两者都应按完整设备成本评估。

## 8. 建议决策

按当前提交物的成熟度，**B可进入排序/归并能力与资源布局验证；A应先补齐算法闭环，暂不能按其预算开始整算子实现。** 这是工程准备度排序，不是宣告B性能胜出。

若继续完善A，先交付三项：

1. 画清每条跨核消息、所在存储、同步与阈值/偏移返回路径；明确kernel边界和所有缓存生命周期。
2. 选定S4的精确算法，并给出b=N、q=1、同分、量化的完整最坏路线与正确性依据。
3. 用可识别的向量hist调用或可分析的真实lowering证明能力；再用同环境单元实测和完整路径校验预算。单看无atomic不足以过关。

我的B也必须承担对称要求：证明完整键与索引语义在向量原语中成立，核实实际打包/scratch，测量局部排序和归并总成本。若其硬件表达差或超预算，就应否决/重新选择，不能因为是我的方案而继续投入。

当前还不能选择性能赢家。A若补齐后确实以低成本完成阈值与收集，可能优于排序方案；应依据新证据调整优先级，而不是坚持先提出的方案。
