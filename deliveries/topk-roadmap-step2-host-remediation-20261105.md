# 第2步：宿主预约配置处理要求

## 当前状态

公共CPU收据已通过。宿主检查确认：共享锁在宿主存在，但yjl不可见；yjl为独立PID命名空间，候选路径无guard。详见[原始结果分析](../experiments/topk/20261105-roadmap-step2-host-inspect-112739/analysis.md)。本轮没有改变环境或调用NPU。

## 为什么不再发一个BMM重试命令

预约前置条件没有变化，重跑只能再次阻塞。把仓内guard复制进容器、创建同名私有锁或设置一个环境变量，均不能使容器获得真实宿主预约/进程可见性。不得绕过公共launcher，亦不改公共require_reservation检查。

## 站点需要落实的配置

1. 确认宿主现有共享锁属于统一设备预约机制；保留原锁，不删除、不重新初始化，不据mode666推导没有占用。
2. 明确站点审计过的Python guard入口及其源码版本。维护者目标仓4409536e自带scripts/npu_guard.py可供审查，但不能仅因文件存在就声称部署/站点审计已完成。
3. 让验证环境访问真实宿主共享锁目录和合规的宿主进程视图。文档方案通常为共享/run/lock/ascend-npu和host PID；其他等效方案须由站点给出所有权/进程验证证据。
4. 确认950PR/CANN9.3作为开发正确性环境的适用范围，仍不能声称已匹配canonical工具链锁。

## 涉及现有容器时的保留要求

先记录现有容器完整运行配置、设备映射、网络、挂载及镜像信息。完整docker inspect可能包含令牌/密码，应仅在服务器本地保留，不上传。不要为了分享配置而上传环境变量或认证信息。

Python/CANN/TileLang可能在yjl可写层，不可以直接以原镜像重建。变更前必须保留可写层和数据，并确认回滚方式。/home已是bind挂载，但这不代表容器内其他路径自动持久化。不要执行docker rm、prune或reset设备。

host PID及新增挂载通常涉及重新创建容器；docker update不能直接将现有PidMode改为host。停机、更改隔离边界及共享配置前，需要服务器使用者/站点确认维护窗口。当前证据不足以给出精确且可回滚的重建命令，本文件不提供猜测模板。

先检查新环境可见同一个共享锁与宿主进程，并确认guard的所有权验证；随后在冻结目标源码4409536e上补公共BmmFwdOp --verify-only。不需要再次重跑已通过的CPU检查，除非源码/环境发生了会影响它的变化。公共BMM收据通过后，才进入第3步TopK后端接入。

在配置落实前保持第2步阻塞，不恢复性能优化。用户能够进入宿主终端不等于可以无停机影响地改造现有容器，也不等于维护者站点配置已经通过审查。
