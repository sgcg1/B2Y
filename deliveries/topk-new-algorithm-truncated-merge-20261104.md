# 新算法方案：分块精确排序与截断归并TopK

2026-11-04。用户要求从整体重新选择算法，而非继续修补旧radix流程。本方案明确选择独立的比较/归并路线；不继承粗FP16桶、候选缓存阈值、hist→prepare→compact→finish或溢出fallback。它是经典算法在当前规格上的新实现方案，不宣称研究意义上的新发明。

**交付状态：算法、正确性证明和独立CPU可执行原型已完成；NPU TileLang内核尚未实现，没有新性能数据。** 不能将CPU排序/归并原型称为已经获得设备加速。

## 1. 决策与输入输出

目标仍是同环境950PR上N16384、K2048、FP32全窗口，稳定优于原生TopKV2的本轮10.639μs。保留完整精度、绝对索引与既有特殊值/tie语义；输出允许有序，因此可以直接返回有序TopK，不需要打散。

选择P=4，每块4096项。每块独立产生本块有序Top2048；随后二叉截断归并，任一归并节点只保留前2048项。

```text
4096项 ─ 局部Top2048 ─ L0 ─┐
                           ├─ MergeTop2048 ─ M01 ─┐
4096项 ─ 局部Top2048 ─ L1 ─┘                      │
                                                  ├─ MergeTop2048 ─ 最终2048索引
4096项 ─ 局部Top2048 ─ L2 ─┐                      │
                           ├─ MergeTop2048 ─ M23 ─┘
4096项 ─ 局部Top2048 ─ L3 ─┘
```

该算法所有输入走同一种选择结构。同分、量化、接近FP32不会让它因为某桶超过2048而切换到全行radix重扫。短窗口只改变有效长度与最后padding，不改变正确性依据。它的代价主要随N、K及层数变化，数据分布仍可能影响比较/归并细节，不能据此宣称耗时完全恒定。

## 2. kernel A：四块并行的局部精确TopK

每个block负责连续4096个原始位置：

1. 只读取一次负责区域的FP32分数，生成原绝对索引；窗口外项不参与有效候选集合。
2. 构造可精确比较的完整键，保持FP32全部排序信息，不转FP16。
3. 将小tile排序为有序段，再做本block内部的归并树。任一节点只保留min(K,节点有效长度)项。初始tile32用于CPU说明，不把32视为已确认的950PR最佳指令宽度。
4. 最后4096→2048的局部归并只输出前2048，不生成后2048项；写出L0/L1/L2/L3。

全窗口产生8192个候选，逻辑记录为uint32完整分数键+int32绝对索引，共64KiB。偏移固定，无需逐项atomic申请位置。部分窗口记录每段有效长度，最多额外4个int32；不能把无效项当成合法负无穷参与排序，否则可能挤掉合法-inf。

**不能改成每块只保留512项。** 全局2048个赢家可能全部在第一块，局部512会永久丢失1536个赢家；CPU验证包含该反例。每块保留K是最坏分布下安全剪枝的依据，而非假设赢家均匀分布。

## 3. kernel B：两层截断归并

初始可落地设计为单个block内部完成三个归并节点；这是执行基线，不预先宣称单block一定能达到目标。

- 第一层：M01=MergeTopK(L0,L1)，M23=MergeTopK(L2,L3)，各保留2048。
- 第二层：result=MergeTopK(M01,M23)，保留2048，最后只写索引。
- 只有kernel A与B之间需要设备级完成依赖；中间M01/M23留在B内部，不为每层再启动设备kernel。

归并需要使用成批比较/向量归并。不能把CPU原型的逐个Python取头循环直接翻译为单线程设备循环，否则只是换了算法名字，却继续牺牲向量执行。

一种明确的分批归并规则：从左右有序段各取最多R项（初始设计R=256，尚未调优），合并这两个有序头块，只输出其中前R项；统计这R项分别消费了左右多少个元素，按实际消费数推进两个读指针。最终一批按剩余quota截断。**不能每批无条件同时推进左右各R项。** 头块未被输出的项必须保留或重新载入，不能丢弃。

正确性理由：每段头块之外的项在本段中已有R项不小于它，因此它不可能出现在两段并集的下一批前R名中。按消费数推进后重复，即可精确生成全局前K。等分数时用索引构成全序，消除歧义。边界长度不足R时按真实长度处理。

本规格B中的三个节点各最多输出2048项，共6144项逻辑归并输出。R256时每个满长节点8批，共24批；这不是24次设备kernel，也不是24条硬件指令。实际向量merge/compare/scan调用及寄存器布局仍需验证。

## 4. 全局正确性证明

令≻为完整分数降序、同分原索引升序的全序。

局部剪枝：若x未进入所属块TopK，该块已经有至少K个元素≻x；它们在全局仍优于x，所以x不可能进入全局TopK。

归并剪枝：若x不在某个子集合并后的TopK，该子树已经有K个元素≻x；加入其他子树不会使x进入全局TopK。因此每个内部节点保留K项安全，归并树根得到精确全局TopK。

该证明不依赖随机分布、不依赖FP16近似桶、也不依赖哪个块有多少赢家。参考实现按完整有序结果核验，而不是只核验结果数量。

## 5. FP32、NaN、同分与窗口语义

完整分数键沿用数值契约：NaN统一为最大键、±0视为同分，其余值包括±Inf按完整FP32数值排序。同分按更小原绝对索引优先。

实现可以比较(key,index)二元组，或使用能证明等价的稳定排序/归并；不能把索引挤入FP32小数位，也不能只对FP16排序。普通浮点排序对NaN的行为不自动等于该契约，硬件原语若不能表达所需比较语义，就必须增加正确的键比较/特殊值处理，并把成本计入。

短窗口输出全部有效项，剩余用N=16384填充；空窗口全部padding。有效段长度必须独立于padding分数表示。CPU原型已覆盖跨分块边界窗口与合法-inf，不借用旧radix实现作为oracle。

## 6. 成本与真实风险

算法形态是分块排序/选择加有界归并，比较模型约O(N log(N/P)+PK)，不是假装线性算法。它以可向量执行、无热点直方图、无桶容量退化、明确的有序归并结构换取更多排序工作。

全窗口的逻辑GM流量预算：读原分数64KiB，写候选64KiB，读候选64KiB，写最终索引8KiB，共**200KiB**；不含padding、真实物理记录打包和其他元数据。不能声称新路线必然比旧路线少搬数据。

B若一次保存全部输入、中间和最终记录，逻辑空间为64+32+16=112KiB，另加原语scratch；可通过流式头块和复用降低峰值。A的双缓冲及sort scratch也必须计入。**8字节逻辑记录不等于硬件Sort/Merge的物理打包大小**，某些原语有额外字段/对齐，不能据112KiB直接宣布一定放得下。

P4是针对本规格的初始选择，不是增加核数越多越好：P≥8时块长≤K，局部TopK将保留全部输入，候选回到16384项。P4将候选降至8192项，仍有明显归并代价；这一代价可能使方案无法超过TopKV2，必须实测。

官方[TopK文档](https://asc.gitcode.com/api/SIMD-API/adv_api/sort_operations/TopK.html)确认存在排序路线，950PR/950DT的相关路径使用Sort。这证明硬件排序值得评估，不证明当前TileLang后端已支持所需完整键排序、归并与消费数统计，更不证明我们的新方案能在10.639μs内完成。

## 7. 已实现与接下来的工程边界

独立[CPU原型](../analyses/topk/20261104-truncated-merge-design/reference.py)已实现完整分块tile排序、逐层截断归并与窗口padding，30个规格级测试通过，结果见同目录validation.json。oracle直接按数值/NaN类别/绝对索引全排序，不复用分块算法或旧radix路径。测试含随机、全同分、四级量化、升降序、赢家集中单块、NaN/Inf/±0、空/短/2048/2049/跨块窗口及混合分布。

新NPU实现应作为独立入口，不在旧decode_finish上继续加开关。下一步工程顺序是：

1. 检查当前TileLang后端能否生成满足全序的向量tile排序、批量归并及消费数统计，核对生成代码与实际scratch布局。
2. 先落地局部TopK与两路MergeTopK两个能力单元，做正确性与硬件表达验证；不在此阶段拿CPU原型计时宣称性能。
3. 按本方案组合两kernel完整路径，与旧实现和同环境TopKV2比较，沿用现有设备任务计时和证据协议。
4. 如果硬件表达退化为标量比较，或sort记录布局/归并代价已超预算，明确否决该实现；不要用外部原生TopKV2代替TileLang新算子来制造达标结果。

本文件取代上一份审查中“优先继续向量阈值选择”的实现优先级：当前选定的新候选是**比较排序/截断归并**。算法正确性已经有证明和CPU原型，设备可行性及性能尚未验证。这是从零选择的新执行骨架，不是旧粗桶方案的小修补。
